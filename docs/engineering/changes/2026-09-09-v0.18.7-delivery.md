## Plan v3: approved R2 category priority

After observing the native Espresso/coffee-store routing, the user explicitly approved category priority. This is a new business rule, not an inferred approval of the original NF07 zero-relevance proposal. R1 was delivered and tested but no v0.18.7 release tag exists, so retain semantic 0.18.7 and use a new R2 cache suffix after these changes.

Research confirms that ordinary text, continued requests and resolved Shopify URLs already forward the top-level productType through the Woo DTO and controller. A legal visual request can supply only `visualInput.productType`; the current Woo request omits this nested type. The minimum fix forwards top-level type first, then the existing validated visual type, only in the Woo request. It does not write inferred type back into stored hard requirements or change public DTOs. Backend classification must distinguish compatible, clearly conflicting and unknown metadata; neighboring categories are not automatically incompatible.

The two implementation routes are a narrow controlled category vocabulary within the existing planner or a new hierarchical registry schema with a data migration. Choose the former: no new schema, no registry/trust migration, conservative UNKNOWN for unsupported semantics. Detailed backend and visual steps are frozen in their separate engineering records before implementation.

R2 sequence: (1) backend planner/controller and public assertions, with source build; independently (2) visual type forwarding and public assertions, with MCP build; (3) independent reviews, new cache suffix, final dual builds/default suite/typecheck/lint; (4) README/design/status updates and link/diff checks; (5) commit, push, actual installation, byte verification and installed stdio; (6) one separately recorded source deployment and same-input native regression; (7) final v0.18.7 tag and release assets.
