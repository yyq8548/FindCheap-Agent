## Authority, baseline and Research

Chris authorized implementation after the capsule audit on 2026-09-08, and expansion from 200 to 1,000 WooCommerce storefronts, prioritizing popular merchants and common shopping categories. This authorizes the described code, data and regression work. It does not automatically publish a release, modify merchant trust, increase network permissions or establish a full local product catalog.

Baseline: `a4d51c7a3155756458f17aafcbf7e45cab82cfb4`, v0.18.2, initially clean tracked worktree. Applicable design: [sections 3, 4.1, 5, 7, 8.1, 10, 11 and 13](../../architecture/agent-design.md). Existing adapters, deterministic identity and ranking, immutable selections, independent source budgets and host-authorized recovery remain.

FACT: the original task `01a08316-6215-7cc0-bbcd-5672d9d771c8` invoked Awin, Shopify and Woo, then returned zero confirmed capsule matches and three Woo research cards. The installed-bundle/production-service reproduction repeats the chicory and green-coffee cards. A separately captured real Shopify response has ten products: four non-USD and six USD. Actual adapter replay drops all six USD because the old coffee classifier requires an optional product category field. The shared coffee helper recognizes three explicit capsule/pod titles. Original receipts and later live observations are distinct evidence, retained in ignored `artifacts/coffee-capsule-audit`.

FACT: `shopify-client.ts` defines the internal port consumed by search orchestration, backend and selected-product handling. `shopify-global-catalog-client.ts` normalizes the catalog response but currently discards pagination; `search-products.ts` asks for the same query and limit in this case, and `SearchRun.read` reuses that result. The [official Global Catalog contract](https://shopify.dev/docs/agents/catalog/global-catalog) accepts `catalog.pagination.limit` (1–50) and a returned opaque cursor. Its `total_count` is estimated. A bounded next page is possible without increasing the existing two-pass source orchestration budget.

FACT: coffee assessment is shared by candidate evaluation and selected-product inspection, but older adapter filtering runs first. Form vocabulary misses explicit primary product forms and chicory/green-coffee evidence. The recommendation layer has no dedicated capsule-system clarification. SourceFailure currently combines local Woo capability/request limits with global recovery vetoes. Public coverage retains the last Woo pass and mixes identity and feature-assessment counts.

FACT: Woo admission is a static storefront access registry consumed by the source service. Existing search caps select up to six shops per pass and two passes. Existing 200-store verification methods, safe readers, domain boundaries and evidence fixtures provide the admission baseline. API admission does not grant official-brand or merchant-trust status. Shared owners with genuinely different brands/catalogs can be separate storefronts; aliases, regional mirrors and duplicate catalogs cannot inflate the count.

ASSUMPTION: broad category priorities are apparel, beauty/personal care, home/kitchen, electronics/accessories, food/coffee, sport/outdoor, pets, toys/hobbies and books/art. Popularity must be supported by named public ranking/merchant evidence when used; lacking comparable traffic data is labeled unknown, not invented.

UNKNOWN: how many new candidates will pass current public Store API, USD, actual product, search/variant, domain and storefront checks. Discovery and admission outcomes will be recorded, including failures; an arbitrary list of 1,000 domains cannot satisfy this task.

## Propose and selected approach

| Dimension | A: source-specific patches and a larger hand-maintained list | B: shared coffee evidence, bounded continuation and verified admission pipeline |
| --- | --- | --- |
| Behavior | Relax Shopify missing category, add Woo exclusions, append verified shops | Converge controlled coffee evidence, keep exact identity rules, continue real source pages, separate local source limits from global safety |
| Benefit | Smaller immediate code delta | Addresses false negatives, false research cards and ineffective recovery together |
| Risk | Duplicate rules and missing diagnostics persist; discovery process scales poorly | More internal consumers require contract and integration checks |
| Data | Individual manual admission retains existing schema | Public discovery candidates followed by safe, bounded reader/controller and product evidence; distinct accepted and rejected records |
| Cost | Lower initial code effort, greater repeated review | Moderate adapter/orchestrator changes; no new runtime service or dependency required |
| Rollback | Revert patch/list additions | Revert independent modules and added registry entries; existing trust and state formats preserved |

Choose B under the user's explicit implementation scope. Recovery remains in the existing MCP SourceFailure contract rather than migrating all Backend sources to a new envelope. For pagination, expose an optional continuation on the existing Shopify port rather than implementing a hidden auto-crawl inside the adapter. This preserves orchestration ownership of request budgets and deduplication.

Internal Shopify contract: input `continuation?: { query: string; cursor: string }`; result `pagination?: { query: string; hasNextPage: boolean; nextCursor?: string; estimatedTotalCount?: number }`.
