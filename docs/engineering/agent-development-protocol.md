# 工业级智能体研发协议

> 2026-09-06：Chris 要求采用 Research → Propose → Plan → Implement → Test 五阶段流程。
> 本协议规定如何研发；[Agent 总设计](../architecture/agent-design.md) 规定产品应该如何工作。协议不能替代总设计，也不表示产品已通过工业级验收。

## 1. 适用范围与硬门槛

所有改动必须符合已批准总设计。发现需求、方案或现有实现与总设计冲突时，明确列出冲突；业务规则、权限或范围需要变更的，先由用户确认并更新设计，不能在实现中悄悄改规则。

代码、接口、依赖、配置、提示词与工具契约的改动按以下五阶段推进。小任务可以压缩记录篇幅，但不省略阶段、不用“改动很小”豁免局部构建及相关自动化断言。已冻结计划内的原子步骤复用已选方案，不为每个文件重复设计；新增范围或推翻原假设时返回相应阶段重新冻结。

纯文档改动也保留五阶段，方案比较针对文档结构与维护方式；构建项可写 `N/A：无运行产物`，改用自动链接、结构／约束检查及 diff 检查。进入产品运行时的提示词、分发购物技能或工具配置不是纯文档豁免项；仅供研发读取的设计与流程文档不触发无关产品构建。只读分析请求停在被要求的阶段，不据此获得修改代码的授权。

每一阶段都必须有可检查的产物和退出条件。推荐状态：`未开始 → 进行中 → 通过`；未通过写 `失败` 或 `阻塞`，不把跳过、未执行或缺少环境标成通过。

## 2. Research — 事实检索

在编写任何实现或测试代码前，先完成客观事实底稿。

1. 读取总设计、适用 ADR、仓库模块布局、工作区配置、依赖声明与锁文件约束，记录分支、源码版本和现有未提交改动。
2. 遍历仓库模块调用与依赖拓扑，区分活跃模块、构建入口和已归档模块；然后沿本次入口追踪“调用者 → 接口 → 实现 → 下游依赖”，反查共享接口的所有受影响消费者。
3. 核对接口的输入／输出、错误、状态归属、调用顺序、身份与权限、超时／重试、配置、持久化和副作用。不能只看类型签名就声称理解完整契约。
4. 查现有测试和回归证据，确认真实构建／测试命令、覆盖范围、外部环境要求与已知失败；需要重现时在批准范围内运行诊断，不发布、不迁移生产数据。
5. 输出事实底稿，明确 `FACT`、`ASSUMPTION`、`UNKNOWN`。每项事实引用文件与符号／行号，运行事实附命令、时间和版本；关键未知项必须查明或作为明确阻塞项处理。

底稿至少包含：本次目标对应的总设计章节、现状调用链、接口与消费者表、依赖约束、影响范围、已有验证、未知项。没有读到或验证到的动态路径要写清，不能声称“全仓库已完整理解”。

**退出条件：**改动入口、影响链、接口约束和验证入口都有证据；没有会改变方案安全性或可行性的关键隐含假设。事实查询可以并行委派，主智能体负责汇总和消解矛盾。

## 3. Propose — 至少两种方案

基于同一事实底稿，对比至少两种真正不同且可实施的架构／接口方案。可以比较“在现有模块内收敛规则”与“经已有 interface／adapter 集中处理”，不必为小需求引入新平台或全量重写。

每种方案说明：

- 改动位置、职责划分和接口变化，以及对总设计的符合性。
- 用户收益、性能／稳定性收益及可验证指标。
- 安全、数据、兼容性、回归与运行风险。
- 重构代价：涉及模块／消费者、迁移、依赖增加、测试及运维成本。
- 撤回或回滚方式，为什么优于／劣于另一方案。

至少给出一张共同维度的比较表和明确推荐。不能把同一方案换名算两案，也不能用明显不适用的重写方案充数；若第二条路线违反已确认硬约束，展示排除证据，继续寻找可行替代或报告无法完成两案比较，不能伪造可行性。

**退出条件：**至少两案完成收益／风险／代价比较，推荐理由可由事实支撑；所选方案及允许自主实施的范围明确。涉及总设计或授权变化时等待用户确认，已有明确批准不重复请求。

## 4. Plan — 冻结时序与依赖

将选定方案冻结成可执行版本，向用户展示范围、步骤与验收。记录执行依据：用户批准的计划，或用户明确授予自主选型和实施的任务范围。

为每个原子步骤记录：

| 字段 | 必填内容 |
| --- | --- |
| 步骤 ID／前置步骤 | 显式依赖关系；只允许无依赖冲突的步骤并行 |
| 模块与接口 | 目标文件、调用者、输入输出、不变量、错误及兼容要求 |
| 最小改动 | 一个可以独立构建和验证的行为增量，不按“大量文件一起改完”拆分 |
| 局部构建 | 已核实的所属包或消费者构建命令及预期产物 |
| 自动化断言 | 测试接口（seam）、具体输入、独立预期、测试文件／命令 |
| 通过与失败处理 | 什么证据允许继续；失败时修复、撤回或返回哪个阶段 |

计划同时冻结必选验证范围、基线、外部依赖、数据迁移／回滚顺序和禁止改动范围。接口先提供兼容合同，再推进依赖消费者；确实不能分开的循环依赖应在动手前调整原子步骤，不在构建失败后临时把所有模块并为一步。

新增测试应在计划确认的公共接口上观察行为；预期来自业务规则、人工确认案例或独立固定值，不复制实现算法来制造必然通过的断言。

**退出条件：**步骤有明确先后关系，每步有接口、构建、断言和完成标准；执行权限充分；计划已冻结。发现新事实改变方案时，保留旧版本及变更原因，重新完成受影响的 Research／Propose／Plan 后才继续。

## 5. Implement — 逐模块实现与立即构建

按冻结计划一次推进一个原子步骤：

1. 对该步骤新增或扩展自动化行为断言。修复缺陷时先确认回归断言在旧行为上失败，且失败原因正是待修问题；不一次写完全部假设性测试。
2. 只实现让该步骤满足合同所需的最小改动，保留无关用户修改。接口、权限或状态约束变化不得偷偷藏在重构中。
3. **每完成一个计划模块的修改，立即执行该模块所属包或受影响消费者的局部构建，并运行该步骤断言。**两者通过后才推进依赖步骤，不能攒多个模块到最后统一构建。
4. 记录源码状态、命令、退出码与结果；失败时停在当前步骤修正。发现计划假设失效则返回 Plan，不边失败边扩散改动。

局部构建是可运行／可打包产物的检查，单独 `typecheck` 不能冒充构建。没有独立构建脚本的共享模块，使用包含该模块的最小所属包／消费者构建；影响多个消费者就验证对应多个产物。并行步骤须先冻结共享契约，划分写入范围并避免同时写同一构建产物，集成后重新验证。

当前命令入口的核对方式见 [package.json](../../package.json)、[MCP 包](../../apps/mcp-server/package.json)、[来源服务包](../../apps/awin-feed-service/package.json)，不要猜测不存在的逐文件构建脚本：

| 改动 | 当前可用构建入口 |
| --- | --- |
| MCP 模块、卡片资源或其依赖 | `pnpm build:mcp` |
| Awin 来源服务或其依赖 | `pnpm build:awin-feed` |
| 两者共享模块 | 按 Research 确认的消费关系执行以上相关构建，并配套类型校验 |
| 纯文档 | 无运行产物；自动链接／结构断言与 `git diff --check` |

这些是当前入口说明，实际执行前仍读取脚本和配置核实。构建产物变化必须与本步来源一致；不使用旧 bundle 的绿色测试证明新源码有效。

**退出条件：**每个计划步骤都有当前源码对应的局部构建与断言通过记录，没有悬空依赖和未解释的计划偏差。测试失败允许继续修当前步骤，不允许将其标为完成。

## 6. Test — 自动化断言与任务闭环

Implement 中的局部验证不能替代最后集成验收。对最终源码和构建产物执行 Plan 冻结的全部必选验证，并生成“需求／规则 → 断言 → 结果 → 证据”对应表。

- 每项行为改动新增或扩展自动化断言；覆盖正常路径、关键边界、错误／拒绝路径及受影响安全不变量。
- 跨模块接口变更运行消费者合同与集成测试；涉及身份、选择、权限、价格、持久化、网络安全或其他核心逻辑时执行完整相关测试。
- 测试通过公共接口观察用户可见行为；来源替身只用于隔离网络与不可控依赖，不能把要验证的业务规则本身模拟为成功。
- 独立预期能识别错误实现；不为过关删除测试、降低断言、事后调整验收分母或伪造真实宿主／图片记录。失败重跑要保留首次失败与修复原因。
- 验证结果绑定最终版本；验证后再次改动相关源码、配置或产物，重新执行受影响验证。

当前 `pnpm test` 使用 [默认配置](../../vitest.config.ts)，排除 `*.integration.test.ts`；`pnpm test:integration` 使用 [独立配置](../../vitest.integration.ts)。默认套件全绿不等于集成测试全绿。所需环境、测试筛选和未执行项必须明示，不能为得到绿色输出连接未经授权的生产环境。

**退出条件：**最终版本全部必选断言通过、各模块构建通过、总设计符合性核对完成，才能称该任务闭环。任何必选项失败、跳过、环境阻塞或尚未执行，都不能写“全部通过／任务完成”；原有失败也需如实报告，不能用改前就失败来冒称当前全绿。

自动断言全绿是必要条件，不替代 [总设计第 13 节](../architecture/agent-design.md) 的独立真实商品与实际 Codex 验收。只完成单项修复就报告单项完成，不声称整个 Agent 达标。

## 7. 记录与交付

涉及核心逻辑或跨模块的任务，在 `docs/engineering/changes/YYYY-MM-DD-topic.md` 保存一份事实—决策—计划—验证记录；小改动可在任务对话中用同一结构简写。没有完成的阶段保留空缺状态，不事后补造已冻结或已通过的证据。

```text
目标与总设计章节：
基线版本 / 原有改动 / 权限范围：
Research：调用拓扑、接口/消费者、依赖、FACT/ASSUMPTION/UNKNOWN、证据
Propose：方案 A / B、共同维度比较、推荐、选择依据
Plan：版本、原子步骤/前置依赖、构建、测试接口/断言、通过标准、回滚
Implement：逐步变更、立即构建、局部断言、失败及修正、计划偏差
Test：最终版本、全部必选命令/退出码/结果、证据、未执行项
结论：完成范围 / 待验收 / 阻塞 / 总设计同步 / 发布是否获授权
```

交付时先报结果，再给关键证据和未完成项。协议文件及开发入口提供可持续读取的约束，不代表已安装自动 CI 阶段门禁；若未来加入 CI enforcement，单独按本协议设计与验收。

研发闭环与发布授权分开：通过 Test 不自动授权提交、推送、部署、版本升级或替换安装缓存。需要发布时按用户明确请求与总设计发布要求执行，分别验证 GitHub、Railway、安装缓存，禁止只完成其中一项就声称全部发布。
