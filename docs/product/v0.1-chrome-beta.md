# FindCheap-Agent v0.1 Chrome Beta

## Outcome and assumptions

- Outcome: a US shopper can ask Codex to search the web once and receive the best three source-linked options among the candidates verified on public merchant pages.
- Owner: yyq8548.
- Risk: R0, read-only public product data.
- Assumption: the user has installed the ChatGPT Chrome extension and explicitly authorizes each run.
- In scope: one primary search plus one conditional refinement search, up to eight public merchant domains, at most eight verified candidates, three ranked options, visible item price, availability, identity evidence, source hostname, URL, and observation time.
- Out of scope: membership, accounts, tax, shipping, delivered price, coupons, affiliate tracking, persistence, cart, checkout, order, and payment.

## Architecture and selected patterns

- Topology: one Codex agent with one bounded Chrome tool path.
- Patterns: tool use, human-in-the-loop authorization, guardrails, and deterministic output requirements.
- No multi-agent system, planner, database, queue, scheduler, or memory is required for this slice.
- State machine: `REQUEST → CLARIFY? → AUTHORIZE → SEARCH → VERIFY → RESPOND`, with every failure terminal and fail-closed.

## Data, tools, permissions, and human controls

- Data classification: public product-page data only.
- Navigation policy: search engines are discovery only. Returned products must come from opened and verified HTTPS merchant-owned pages; non-HTTPS, IP-literal, shortened, redirector, login, and search-result URLs are not product sources.
- Budget: at most two discovery searches, eight merchant domains, eight verified candidates, three ranked options, at most one detail page per merchant, at most three concurrent navigations, one compact extraction per inspected page, and at most one retry for a verified transient browser deadline. Verify five first, then up to three reserves only when needed. Never retry access denial.
- Extraction budget: each page returns at most 12,000 characters of structured evidence. Full merchant-page DOM snapshots are prohibited; one targeted field read is allowed only for an incomplete candidate.
- Permission: explicit, single-run Chrome authorization. It does not authorize sign-in, account access, cart, checkout, or payment.
- Retention: no page HTML, screenshot, browser state, credentials, or observation is persisted by the skill.

## Failure and recovery design

- Missing permission: request authorization and stop.
- Missing Chrome extension: direct the user to **Settings → Computer use** and stop.
- Ambiguous identity: ask one clarification; never promote a similar item as exact.
- CAPTCHA, bot defense, unexpected redirect, or access denial: stop without bypass.
- Missing price or availability: return the verified fields and label the missing field unavailable.
- Ranking: exact requested variant first; direct merchant before third-party marketplace; visible in-stock before unknown or out-of-stock; then lower visible item price. Return fewer than three rather than filling with weak matches.
- Condition policy: absence of a condition label does not exclude an otherwise exact offer. Label it `CONDITION_UNCONFIRMED`, rank it after verified `NEW`, and exclude only an explicitly conflicting used, refurbished, renewed, or open-box condition.
- Product-page redirect: accept the candidate only after the final HTTPS merchant hostname and visible identity are verified.
- Unrelated recommendations: return no relevant result instead of presenting them as matches.
- Transient browser deadline: re-check the expected merchant host and visible block state, retry once, then terminate safely.
- Rollback: uninstall the personal plugin or revert the v0.1 skill commit. No external data requires compensation.

## Evaluation and release gates

- Baseline Golden set: 20 Best Buy searches spanning exact model, SKU, ambiguous variant, no result, and blocked access. This remains historical regression evidence, not proof of web-wide merchant coverage.
- Web-wide release gate: repeat the Golden evaluation across at least three merchant domains before promoting the expanded scope beyond the one-user local beta.
- Task success threshold: at least 85% correct bounded outcomes on reachable pages.
- Identity precision: at least 98% for results labeled `EXACT`.
- p95 discovery-page latency: at most 15 seconds. p95 end-to-end latency for the initial five-merchant workflow: at most 90 seconds; adaptive reserve mode may use up to 120 seconds.
- Hard invariants: zero sign-in, account, cart, checkout, payment, unverified product-source URLs, CAPTCHA bypass, fabricated price, or member-price claims.
- Every returned product must include source URL, source type, observation time, and item-price limitation.
- Release status is `LIMITED GO` only after static validation and a real authorized-Chrome happy-path smoke test pass.

## Rollout, observability, and rollback

- Rollout: local personal plugin → one-user pilot → curated regression review → v0.1 release.
- User-visible trace: query, terminal status, result count, source URLs, and observation time; never credentials or raw browser state.
- Roll back immediately on any prohibited action, unverified redirect, personal-data exposure, or fabricated price.
- Owner stops the pilot by removing or disabling the personal marketplace plugin.

## Implementation milestones

1. Encode the v0.1 contract in the plugin Skill and manifest.
2. Add deterministic contract tests and plugin validation.
3. Install in the personal marketplace and start a new Codex task.
4. Run one authorized web search across at least three merchant domains and record only pass/fail evidence.
5. Keep the existing official API adapter dormant until a valid API Key is available.

## Acceptance criteria and open decisions

- A prompt explicitly authorizing Chrome triggers one bounded web-wide lookup.
- At most three ranked cards are returned, each with identity status, URL, observation time, ranking reasons, and price limitation.
- Results are described as best among inspected candidates, never as exhaustive proof of the best price on the entire internet.
- Member price and all purchase actions remain unavailable.
- Denied permission or blocked access terminates safely without fallback scraping.
- Open decision for v0.2: choose the first approved API or affiliate feed and define its legal retention policy.

- Best Buy Golden regression on 2026-08-17: 20/20 task success, 16/16 exact precision, 11.3-second p95 total latency, zero terminal errors, and zero safety violations. Web-wide multi-merchant validation is still required, so rollout stays limited to one user.
- Manual multi-merchant trial on 2026-08-17 at 17:56 ET: Sony, Best Buy, and Target product pages produced three source-linked exact options. A lower Best Buy Marketplace snippet was not represented as Best Buy's direct offer; the verified direct Best Buy product page price was used.
- AirPods timing baseline task `01a011ca-6891-7263-b27a-f6edc936a067`: 148.4 seconds end to end. Search and five sequential merchant browser calls consumed about 29.1 seconds; repeated full DOM output and orchestration dominated the remaining time. The next run must use three-wide bounded navigation plus compact extraction and target 60–90 seconds without reducing five-merchant verification.
- Optimized AirPods task `01a011d3-6ba7-77a1-ad73-d41c69556fc6`: 141.9 seconds end to end. Browser work fell to about 15.8 seconds, but serialized listing/detail follow-ups and repeated reasoning left about 126 seconds outside browser execution. The next run must discover direct product pages, navigate all candidates in one three-plus-two browser call, extract each page once, and rank locally. New, refurbished, and used offers remain separate.
- Condition-filtered AirPods task `01a011dd-d112-7cb3-816c-80a71e5fcac9`: 173.4 seconds and only one verified new result. The primary search found three direct product pages, then stopped; Amazon exposed a used offer and Best Buy did not visibly bind the current price to new condition. A 30-second Chrome connection timeout also inflated latency. When primary discovery has fewer than five direct or three condition-compatible candidates, run one refined broad-web search, retain the five-merchant verification cap, and extract all pages concurrently.
- Sony XM5 task `01a011f3-7114-7530-99aa-dbe3c0164335`: the explicit-model turn completed in 88.4 seconds and verified five merchants with 3+2 navigation plus concurrent extraction, but only Best Buy and Verizon passed. Preserve that fast first batch; when fewer than three pass, inspect up to three reserve merchants and report a reason for every rejected inspected candidate.
- Sony XM6 task `01a01249-6960-7112-8039-1260956947d3`: Amazon, Focus Camera, Walmart, and ShopAtSC were excluded solely because their current offers did not visibly say `New`. This was overly strict. From the next plugin build onward, unlabeled condition is `CONDITION_UNCONFIRMED` and remains eligible after verified `NEW`; explicit used/refurbished/open-box evidence still conflicts with a new-product request.
